Guidance for Claude Code when working in this repository. Read the whole file before changing
anything. The design spec this repo implements lives at
`~/.claude/plans/research-about-the-company-robust-puppy.md` (the "Decision summary" and
sections 3.x are authoritative; earlier phases are history).

## What this is

FinRecur: when a reconciliation agent keeps escalating the same kind of exception, it groups
them, names the cause, proposes a fix from a fixed menu, dry-runs it (with side effects), gets
human approval bound to the exact data snapshot, applies it in a transaction with invariant
checks, and tracks whether the condition comes back. Data is a real Olist slice plus labelled
injected faults. It is a demo, and the README says plainly what is real, simulated, and out of
scope. Don't add hype to it.

## Commands

```bash
make dev            # postgres (compose) + uvicorn --reload on :8000 + next dev on :3000
make db             # postgres only
make seed           # import Olist slice + apply data/faults.json in demo mode
make test           # pytest (backend) + vitest (web)
make e2e            # playwright, single path, Claude served from cache
make eval           # scripts/eval.py against the seeded DB -> eval_report.{json,md}
make lint           # ruff check + ruff format --check + pyright + eslint + tsc --noEmit

cd backend && uv run pytest -x -q          # fast backend loop
cd backend && uv run alembic revision --autogenerate -m "..."   # after model changes
cd backend && uv run alembic upgrade head
cd web && npm run dev
```

After any non-trivial change run `make lint` and `make test`. After touching models, run the
alembic pair and check the generated migration by hand (autogenerate misses enum changes).

## Architecture

Two processes plus Postgres. `backend/` is Python 3.12 / FastAPI / SQLAlchemy 2 / Alembic.
`web/` is Next.js (App Router, TypeScript) calling the API over HTTP. Postgres 16 via
`compose.yml`.

**The pure core.** Everything under `backend/finrecur/` is plain functions: rows in, decisions
out. No SQLAlchemy sessions, no HTTP, no env reads.

- `importers/` — source → canonical `Receivable` / `Receipt`. `olist.py` is the first; a
  CSV/XLSX importer plugs in the same way. Identity is Olist `customer_unique_id`, never
  `customer_id`.
- `rules/` — R5 group → R1 exact → R2 amount+date → R7 rounding → R3 short-pay → R4 tolerance →
  R6 overpayment → R8 escalate. First rule that settles a receipt wins. Rules read a policy dict;
  they never hard-code thresholds.
- `grouping/` — 4a bucketing on computed features over open exceptions **and** auto-applied
  write-offs (the agent audits its own write-offs; a permissive rule must not hide a systematic
  leak). 4b `explain` is the only place Claude names a cause.
- `fixes/` — the F1–F7 menu, parameter validation, inverse generation, widening detection and
  F6 bounds. `propose` is the only other place Claude is called.
- `dryrun/`, `verify/`, `recurrence/` — prediction, invariants, condition signatures.
- `claude/` — the Anthropic client, response schemas, and the input-hash cache. Cached
  responses are committed under `backend/tests/fixtures/claude/` so CI never needs a key.
- `reports/` — the per-run JSON report, generated by code, no LLM.

**The shell.** `backend/api/` holds thin FastAPI routes and a service layer that loads rows,
calls the core, and writes results inside transactions. `backend/api/models.py` is SQLAlchemy;
`backend/alembic/` migrations are the source of truth for the schema.

**Boundaries that tests enforce.**
- `data/faults.json` is read only by `scripts/seed.py` and `scripts/eval.py`. An
  import-boundary test fails if anything under `backend/` imports or opens it.
- `finrecur/` never imports from `api/`. Same test.

## Hard rules

- Claude is called in exactly two places: `grouping.explain` and `fixes.propose`. Its output is
  validated against a Pydantic schema, then against the actual rows (every id must exist and
  belong to the group it was given; it may drop members, never add). Claude never writes to the
  database, approves anything, or grades its own fix.
- Money is integer centavos everywhere. No floats in amounts, ever.
- The ledger is append-only. There is no DELETE route for `LedgerEvent`, `Approval`,
  `PolicyVersion`, or `Verification`. Reverts insert new rows.
- Approval binds to `snapshot_hash` (balances, allocations, statuses, aliases, full rule
  settings). Recompute inside the apply transaction; mismatch refuses the apply.
- A widening `amend_policy` needs two distinct approver names. Widening = R2 window up, R3
  threshold up, R4 percent up, a cap removed, or any edit the detector doesn't recognise.
- F6 bounds: one amendment moves a value at most 25% of its current value; percent rules never
  exceed 5%; a widening needs a cluster of at least `MIN_WIDENING_CLUSTER` members.
- Every generated date, name, or reference carries `simulated=True` and the UI shows it.
- "Reviewed by" is set only by an explicit review or resolve action. Opening a row never sets
  it. Untouched rows render "Auto · policy vN".
- Roles are a cookie switch. Say "simulated roles" wherever they appear. They are not auth.
- Without `ANTHROPIC_API_KEY` the whole workflow still runs; clusters show "Grouped by code ·
  not yet explained" and a reviewer can pick a fix type by hand.

## Style

Match the existing code, and when there is none yet, match these (they're how Kush's other
repos are written):

- Validate at the boundary (Pydantic on every route, zod on the web side), then trust the types.
- Service functions return a result object (`Ok(value)` / `Err(reason)` in Python, `{ ok, data }
  | { ok: false, error }` in TS), not exceptions, for expected failures.
- Degrade honestly: if a dependency is missing, label the gap in the output. Never crash, never
  pretend.
- Comments explain *why* when it isn't obvious from the code. No comments that restate the
  line. No docstrings that restate the function name.
- Small modules with one job. No abstractions for a single caller. No config for things that
  don't vary.
- Tests test behaviour on real rows from the seeded slice or small literal fixtures. Don't write
  tests whose only assertion is that a mock was called.
- Web: semantic CSS tokens, dense tabular layouts, right-aligned numbers, monospace for ids and
  money, display font only on `/about`. Load the `frontend-design` skill before any UI work.
- Prefer the standard library and the few dependencies already in `pyproject.toml` /
  `package.json`. Adding a dependency needs a reason in the commit message.

## Anti-slop

- No "robust", "seamless", "leverage", "cutting-edge", "comprehensive", "powerful". Say what it
  does.
- No emoji in code, comments, commits, or docs.
- No `try/except` around code that can't raise. No `Optional` on things that are always
  present. No `# type: ignore` without a reason on the same line.
- No README sections that don't answer a question a reader has. The README must always say
  what's real (Olist), what's simulated (faults, roles, generated fields), and what's out of
  scope (FX, chargebacks, credit notes, deposits, real auth).
- When unsure what the spec means, ask. Don't pad.

## Git

- Never `git add -A` or `git add .`. Run `git status` and `git diff`, then stage named files.
  Never stage `.env`, database files, `node_modules`, caches, or generated reports unless the
  change is about them.
- Git is read-only by default. `status`, `log`, `diff`, `blame` are always fine. Commit, push,
  reset, rebase, branch deletion, or any `--force`: only when explicitly asked, one at a time,
  never as an implicit "wrap up" step.
- Before writing a commit, read `git log --oneline -20` and match the existing style. No
  attribution trailers. No conventional-commit prefixes unless the history already uses them.
  One-line messages for small changes.

## Gotchas

(Grows as they're hit. Keep entries short: symptom, cause, fix.)

- Claude fixtures stop replaying after `make seed`: the input hash contained per-seed UUIDs.
  Source rows now get deterministic ids via `finrecur/ids.py` (`stable_id`), and cluster
  evidence is keyed by receipt id, not by the per-run exception id. Keep it that way.
- A run took minutes: a `session.flush()` per receipt against Docker Desktop's slow volume.
  Dependent rows are collected and added after one flush; the dev Postgres runs with
  `fsync=off` (compose.yml). Never add per-row flushes back.
- Seed fails with a FK violation on `receipts`: runs/decisions reference source rows. The seed
  truncates every table with CASCADE; don't replace that with ordered deletes.
- Claude proposed placeholder ids ("<UNKNOWN>"): the fix was to supply candidates in the
  features (candidate canonical counterparties, candidate receivable sets) and reject any id
  not in the supplied rows. If a new fix type needs an id, code must offer the candidates.

- Python on this machine is 3.14; the project pins 3.12 (`.python-version`). The virtualenv is
  a standard venv at `backend/.venv` (created by `uv sync`). Either `source backend/.venv/bin/
  activate` and use plain `python`/`pytest`, or prefix with `uv run`. Both hit the same env.
- Circular FK (runs → clusters → fixes → policy_versions → runs): `policy_versions.fix_id` is
  created with `use_alter=True` and added by ALTER in `0001_initial`. Autogenerate will try to
  inline it again; don't let it.
